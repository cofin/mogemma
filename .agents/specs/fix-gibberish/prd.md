# PRD: Fix Gemma 4 Gibberish Generation (Logits Soft-Capping)

## Overview

The user reported that the Gemma 4 implementation generates gibberish text, exhibiting similar symptoms to a past regression in Gemma 3. Investigation confirms that the issue is due to missing **logits soft-capping** in the final projection layer.

Like Gemma 2 and 3, Gemma 4 is trained with a `final_logit_softcapping` value (typically `30.0`). The logits output from the final matrix multiplication must be bounded using the formula:
```
logits = 30.0 * tanh(logits / 30.0)
```
Failure to apply this capping causes the raw logits to diverge significantly from the training distribution, which leads to numerical instability during softmax and subsequent gibberish outputs.

Currently, `tanh` is imported in `src/mo/mogemma/layers.mojo` but never used. Furthermore, `final_logit_softcapping` is missing from the synthesized `config.json` generated by `src/py/mogemma/convert.py` and is not parsed by the Python `model.py` loader to pass to Mojo.

## Root Cause Analysis

1. **Config Synthesis (`src/py/mogemma/convert.py`)**: The `_VARIANT_CONSTANTS` dictionary for Gemma 4 fails to emit the `"final_logit_softcapping": 30.0` field, causing the Python loader to ignore it.
2. **Python Loader (`src/py/mogemma/model.py`)**: The model loader does not parse or transmit the `final_logit_softcapping` configuration down to the Mojo core backend.
3. **Mojo Engine (`src/mo/mogemma/core.mojo` / `layers.mojo`)**: The final LM head matrix multiplication (e.g., `backend.vec_mat_mul(out_logits_ptr, norm_out, lm_head_ptr, hidden_size, vocab_size)`) returns raw logits directly. The required `tanh`-based clamping is entirely absent.

## Proposed Changes

### 1. Update `convert.py` to Emit Soft-Cap
In `src/py/mogemma/convert.py`, update `_VARIANT_CONSTANTS` so that `"final_logit_softcapping": 30.0` is included for all Gemma 4 variants (`base`, `ple`, `moe`).

### 2. Parse Soft-Cap in Python Runtime
In `src/py/mogemma/model.py`, read `final_logit_softcapping` from the parsed `config.json` (defaulting to `30.0` if not present to ensure backward compatibility) and add it to the initialized `llm` dictionary passed to the Mojo core.

### 3. Implement Logit Capping in Mojo Core
In `src/mo/mogemma/layers.mojo` or `core.mojo`, immediately after calculating the final logits:
1.  Check if `final_logit_softcapping` is greater than `0.0`.
2.  If so, iterate over the `vocab_size` elements in the `out_logits_ptr` buffer.
3.  Apply the transformation:
    ```mojo
    var inv_cap = 1.0 / soft_cap
    for i in range(vocab_size):
        var val = out_logits_ptr.load(i)
        out_logits_ptr.store(i, tanh(val * inv_cap) * soft_cap)
    ```
4.  Ensure this is executed effectively across both CPU and GPU backends. For GPU, a small custom kernel or a loop might be needed in `gpu_context.mojo` to scale the logits before copying back to host.

## Success Criteria
- Deterministic Nano parity gates pass (`test_deterministic_token_parity`) if they were previously failing due to this numerical drift.
- Validating the model via `tools/validate.py --mode llm` outputs coherent answers instead of gibberish.
- The `final_logit_softcapping` parameter flows correctly from `config.json` -> Python `llm` dict -> Mojo execution.

## Testing Strategy
- Unit tests: Add assertions in `test_convert.py` to ensure `final_logit_softcapping` is included in the synthesized `config.json`.
- Integration tests: Verify `validate_llm_generation` completes without semantic failures.
